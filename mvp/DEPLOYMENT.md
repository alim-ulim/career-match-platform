# 운영 배포·백업 실행 안내

2026-10-22. 설정과 로컬 테스트 완료, 외부 공개·이미지 빌드·실제 볼륨 검증 미완료.

## Railway 복구 후
1. 신규 프로젝트/서비스만 생성. 기존 backend가 아닌 최신 mvp 소스 사용.
2. 저장소의 mvp 폴더를 서비스 Root Directory로 지정. /mvp/railway.toml 설정 적용을 확인.
3. /data에 새 영속 볼륨 연결. 앱의 DATA_DIR=/data/ulim. replicas=1.
4. .env.example에 따른 변수를 호스팅 UI에 입력. ADMIN_PASSWORD는 사용자 비밀 저장소에 만든 새 값. 채팅이나 Git에 입력하지 않는다.
5. 기본 HTTPS 도메인을 발급하고 PUBLIC_ORIGIN을 정확히 설정. 포트 8766. healthcheck /api/health.
6. 첫 빌드에서 su-exec 설치와 root→node 실행, 볼륨 쓰기 권한, DB 생성을 확인. 권한 오류를 임시 파일시스템 사용으로 우회하지 않는다.
7. 가상 테스트 계정으로 경력·PDF 등록→운영자 검토→공개→다른 회원 비공개 정보 차단 확인.
8. 재시작 후 계정·프로필·PDF 보존, 테스트 프로필 비공개 처리. 실제 전문가로 오인할 정보를 남기지 않는다.
9. 계정의 백업 지원/요금을 확인하고 백업을 켠 뒤 복원 검증.
10. 운영 담당자·데이터 보관·호스팅 안내를 실제 설정과 대조하고 모집 주소 /join?role=expert를 사용자에게 전달.

로컬 QA 데이터·관리자 비밀번호 파일·개인 이력서 원본은 배포하지 않는다. 공개 저장소에는 프로그램 소스만 반영한다. GitHub push는 아직 하지 않았다.

## SQLite 백업
서버를 실행하는 컨테이너 또는 해당 SQLite 파일에 접근 가능한 신뢰 환경에서:

```sh
node scripts/backup.mjs /data/ulim/ulim.sqlite /보호된-백업경로/ulim-새날짜.sqlite
```

백업 경로의 부모 폴더는 미리 준비한다. 파일은 600 권한으로 생성되며 기존 파일은 덮어쓰지 않는다. 실행 중 WAL에 남은 커밋도 스냅샷에 반영하고 무결성을 검사한다. 단순히 실행 중인 ulim.sqlite 파일만 복사하지 않는다. 생성된 사본은 개인정보가 포함된 운영 데이터이므로 공개 소스/채팅 첨부/공개 버킷에 넣지 않는다. 외부 보호 저장소와 백업 삭제 정책은 배포 때 확정한다.

## 복원
1. 운영 서비스 쓰기를 중지하고 서비스가 완전히 종료됐는지 확인한다.
2. 현재 DB를 안전하게 보존한다. 이 단계에서 덮어쓰기/삭제를 서두르지 않는다.
3. 별도 빈 디렉터리에서 백업 사본의 PRAGMA integrity_check가 ok인지 확인하고 앱으로 읽기 검증한다.
4. 운영 복원을 결정한 경우에만 완전히 정지된 서비스의 DB를 검증한 사본으로 교체한다. 이전 DB의 -wal/-shm 파일을 새 DB와 섞지 않는다. 소유권 node:node, 파일 권한 600, 폴더 700 유지.
5. 단일 인스턴스를 시작하고 /api/health와 가입·프로필·PDF를 확인한다. 백업 시점 이후 기록은 복원되지 않음을 확인한다.

이 절차는 복원 시 운영 상태 변경을 포함한다. 실제 복원은 복원 대상·백업 시점을 확인하고 수행한다. 이번 검증은 격리된 가상 SQLite 파일에서 수행했으며 실제 고객 데이터를 변경하지 않았다.

## 테스트 근거
- 자동 통합 테스트 21개 통과.
- 실행 중 WAL 내용 백업→무결성 검사→다른 파일 복원→내용 확인.
- 서버 재시작 후 전문가 계정 로그인·비공개 경력·PDF 등록 상태 보존.
- 실제 Docker 빌드와 호스팅 볼륨·HTTPS는 아직 미검증.
